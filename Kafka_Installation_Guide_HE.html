להתחלה עם קובצי הפרויקט והסקריפטים החדשים פתחו את מתחילים כאן. המדריך שלהלן מפרט גם את פקודות Docker עצמן.

Kafka — מה מתקינים ואיך מתחברים?

ד״ר פאול אברהמי · Python 3.13.12 · uv ו־Cursor

המסלול הראשון: המחברת פועלת ב־Cursor, שרת Kafka פועל ב־Docker על אותו מחשב, ו־OpenSearch ו־Wikimedia נשארים כבויים. אין צורך בחשבון Confluent למסלול הזה.

לשיעור הראשון נשתמש בשרת Kafka מקומי בתוך Docker. המסלול הבא מיועד ל־Windows, כשהמחברת פועלת ב־Cursor באותו מחשב. OpenSearch הוא הרחבה אופציונלית — אין צורך להתקין אותו לשיעור הראשון.

1. סביבת Python והמחברת

כבר עובדים עם Cursor ו־uv? בדקו ש־Cursor נפתח ושבמסוף uv --version מציגה גרסה. אם uv חסר, התקינו לפי מדריך uv הרשמי. ב־Cursor פתחו Extensions באמצעות Ctrl+Shift+X והתקינו Python (ms-python.python) ו־Jupyter (ms-toolsai.jupyter).

פתחו את תיקיית kafka-python-lesson מהחבילה, שבה נמצאים pyproject.toml ו־uv.lock. אם Kernel ישן פתוח, סגרו אותו לפני הסנכרון. במסוף PowerShell של אותה תיקייה:

uv python install 3.13.12
uv sync --locked

פתחו את המחברת ובחרו Select Kernel → Python Environments → .venv, כלומר .venv\Scripts\python.exe. גרסת Python בתא האבחון צריכה להיות 3.13.12.

2. WSL ו־Docker Desktop — רק אם חסרים

בדקו wsl --status. אם WSL אינו מותקן, פתחו PowerShell באמצעות Run as administrator, הריצו את הפקודה הבאה והפעילו מחדש את Windows:

wsl --install

הורידו והתקינו Docker Desktop ל־Windows, לפי דרישות המערכת והאשף, עם WSL 2. פתחו את Docker Desktop, ודאו שהוא משתמש ב־Linux containers והמתינו שמנוע Docker יעלה. אין צורך להתקין בנפרד Java או Kafka על Windows במסלול המכולה.

docker version

צריכים להופיע גם Client וגם Server. אם מופיע Client בלבד או כשל חיבור למנוע, פתחו את Docker Desktop והשלימו את הפעלתו לפני ההמשך. אם הפקודה docker אינה מזוהה אחרי ההתקנה, פתחו מחדש את Cursor ואת המסוף. מקור WSL: מדריך Microsoft.

3. הפעלת שרת Kafka

ב־PowerShell רגיל הריצו פעם אחת; התמונה הרשמית תורד אם אינה קיימת:

docker run -d --name kafka-python-lab -p 127.0.0.1:9092:9092 apache/kafka:4.4.0

אם כבר קיימת מכולה בשם הזה, הפעילו docker start kafka-python-lab. אין צורך למחוק אותה. בדקו מוכנות באמצעות:

docker exec kafka-python-lab /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
$LASTEXITCODE

אם עדיין יש שגיאת חיבור, המתינו כמה שניות והריצו שוב. קוד יציאה 0 פירושו שהבדיקה הצליחה; רשימה ריקה לפני יצירת Topics היא תוצאה תקינה. אם השרת אינו עולה, בדקו docker logs --tail 80 kafka-python-lab. מקור: Apache Kafka 4.4 Quickstart.

4. חיבור המחברת לשרת

ערכו את תא ההגדרות במחברת, ולא את ה־PowerShell:

RUN_LIVE_KAFKA = True
RUN_LIVE_WIKIMEDIA = False
RUN_LIVE_OPENSEARCH = False
BOOTSTRAP_SERVERS = "127.0.0.1:9092"

בחרו Restart Kernel ואז Run All. בניסוי חדש נוצרים Topics עם RUN_ID חדש. לאחר שהשרת מוכן, צפויים מידע אמיתי על המחיצות, confirmed: 10 בדוח השליחה בשלב 5 ו־LIVE processed and committed: 10 בשלב 7. האירועים עדיין סינתטיים; הפעם ההעברה והקריאה נעשות דרך Kafka אמיתי. קריאה מוגבלת יכולה להחזיר פחות רשומות: במקרה כזה בדקו את הפלט והלוגים לפני ההמשך.

5. סיום וחזרה לשיעור

בסיום אפשר לעצור את השרת, ובהמשך להפעיל את אותה מכולה מחדש:

docker stop kafka-python-lab
# Run the next command when returning to the lesson:
docker start kafka-python-lab

לאחר ההפעלה החוזרת בדקו מוכנות שוב. הפקודות אינן מוחקות את המכולה. עצירה והפעלה של אותה מכולה אינן מוחקות כשלעצמן את נתוני המעבדה. רשומות עדיין כפופות למדיניות השמירה של Kafka; אין כאן גיבוי נפרד.

מה נלמד אחרי ההתקנה?

המטרה: להבין מה קורה לאירוע מהרגע שנוצר ועד שמפיקים ממנו תשובה. נעקוב אחרי אירוע אחד מתוך FIXTURE: מזהה synthetic-001, אתר en.wikipedia.org, זמן 12:00:02 UTC ו־bot=True. זהו נתון מומצא לתרגול. הוא יוסיף 1 לספירת Bots ולחלון עשר השניות שמתחיל ב־12:00:00.

ברירת המחדל מקומית: שלושת דגלי RUN_LIVE_... הם False. מעבדים עשרה אירועים ברשימות ובמילונים של Python; לא מתחברים לשרת Kafka. הגדרת פונקציה באמצעות def מכינה אותה לשימוש — היא אינה מפעילה את תוכנה.

במסלול האמיתי: מפעילים שרת Kafka, מאפשרים את הדגל המתאים, ושולחים וקוראים רשומות דרך הרשת. הספרייה confluent-kafka היא לקוח Python, לא שרת Kafka. התקנתה אינה מפעילה שרת ואינה דורשת חשבון Confluent כדי להתחבר לשרת המקומי.

זו התאמה לימודית מקורית ל־Python של ארבעת מודולי Java במאגר Conduktor. הספירות במחברת הן חישובי Python על דגימה; הן אינן הפעלה של Kafka Streams.

חלקשלביםמה לומדים ומה רץ
האירוע1–3סביבה, FIXTURE, ו־encode_event/decode_event: מילון הופך ל־JSON ולבתים וחוזר למילון. הכול מקומי.
העברה וקריאה4–8ensure_topics, publish_json_rows ו־consume_events יופעלו מול Kafka רק עם הדגל החי. כברירת מחדל בודקים מפתחות ועיבוד מקומי; starting_position מסבירה מיקום המשך.
תקלה ויעד9–10process_offline מדמה כשל בזיכרון. index_event כותבת ל־OpenSearch רק כששני הדגלים Kafka ו־OpenSearch מופעלים. היעד קורא מ־TOPIC.
מקור אירועים11–12parse_sse_blocks נבדקת מקומית. read_wikimedia_events מופעלת רק עם דגל Wikimedia. דגל Kafka מעביר את הדגימה דרך WIKI_TOPIC אל ANALYSIS_EVENTS.
תשובות מהנתונים13–16classify_bot ו־aggregate_windows מחשבות ספירות וחלונות. שלב 15 הוא ניסוי סינתטי באירוע מאוחר. שלב 16 מדפיס סיכומים, או מפרסם אותם אם Kafka פעיל.

סדר קריאה נוח: תחילה הריצו לפי הסדר במצב המקומי. קראו 1–3, ואז עקבו בקריאה אחר FIXTURE, ANALYSIS_EVENTS והספירות ב־12–14. לאחר מכן חזרו ל־4–11. בהרצת תאים אין לדלג על ההגדרות שעליהן תאים מאוחרים מסתמכים.

החלופה בענן: Confluent Cloud

חלופה לשרת המקומי: Confluent Cloud. פותחים חשבון, יוצרים Kafka cluster, מקבלים כתובת bootstrap.servers ומייצרים Kafka API key ו־secret עם הרשאות מתאימות. בתצורת מפתח API הלקוחות משתמשים ב־SASL_SSL ובמנגנון PLAIN; את הסודות שומרים מחוץ למחברת.

המחברת הנוכחית מוגדרת לשרת המקומי. מעבר לענן דורש להוסיף את תצורת האימות וההצפנה ל־AdminClient, ל־Producer ול־Consumer. שינוי כתובת השרת לבדו אינו מספיק. גם replication_factor=1 של מעבדת השרת היחיד דורש התאמה: Confluent Cloud משתמש בשכפול של 3. ההוראות כאן אינן מפעילות ענן ואינן מציגות את הקוד המקומי כמוכן לחיבור אליו.

להתחלה עם החבילה הזו בחרו במסלול Docker שלעיל; אין צורך בחשבון Confluent בשבילו. מקורות: לקוח Python וחיבור ל־Confluent Cloud; שכפול ב־Confluent Cloud.
